# 第一部分：必须知道的两个硬伤

## 硬伤 1：数据泄漏 —— 你已经上线展示的准确率是虚高的

### 原来是什么

你的项目里有三个数据文件：

| 文件                | 条数     | 出现位置                 |
| ----------------- | ------ | -------------------- |
| `large_data.csv`  | 10,800 | `visualize.py` 读它做评估 |
| `large_data2.csv` | 7,766  | `train.py` 读它做训练     |
| `data.csv`        | 102    | 早期用的小样本              |

`train.py` 第 12 行 `DATA_PATH = 'large_data.csv'`（注：注释写的是"大数据集"），  
而 `visualize.py` 第 14 行读的也是 `large_data.csv`。

### 为什么是问题

我实际检查后发现两件事：

1. `large_data.csv` 内部有 **1,703 条完全重复的评论**；
2. `large_data2.csv` 有 7,766 条，它是从 `large_data.csv` 里切出来的子集。

这意味着：**当你用 `visualize.py` 跑 `large_data.csv` 得到"混淆矩阵"和"准确率"时，  
这份数据的绝大部分（7,766 条）是模型在训练时已经见过答案的。**

这就是**数据泄漏（Data Leakage）**。后果是那句准确率数字不代表模型的真实泛化能力，  
它反映的是"模型背书背得好不好"。

为什么这件事最致命？因为**只要你把模型交付出去，这个数字就会崩**。  
答辩老师或面试官只要问一句：

> "你的测试集是怎么划分的？和训练集有重叠吗？"

这个项目就当场失分了。这不是技术细节问题，是**科研诚信**问题，  
评委对这个的敏感度极高。

### 改成什么

我重写了整条数据链路（`v2/src/data.py` + `prepare_data.py`），核心是三步：

**第一步：全局去重。**  
把 1,703 条重复样本删掉。重复样本是泄漏最常见的来源——  
同一句话如果既在训练集又在测试集，模型就"背过答案"了。

**第二步：三路划分并物化落盘。**  
不再"每次运行时随机切"，而是切成三份固定文件写进硬盘：

```
v2/data/train.csv   7277 条   ← train.py 只读这个
v2/data/val.csv      910 条   ← train.py 用它早停，evaluate.py 用它拟合校准
v2/data/test.csv     910 条   ← 只有 evaluate.py 能读
```

**第三步（关键）：物理隔离。**  
`train.py` 的代码里根本没有出现 `CFG.test_file` 这个变量。  
它想读测试集都读不到——**这在工程上叫"用架构保证正确性"，而不是靠人的自觉。**

### 收益

- 泄漏自检 `leak_check()` 自动验证三组交集，输出报告到 `split_report.json`
- 现在汇报的指标是**真实泛化能力**，随时可以被第三方复现

### 答辩怎么讲

> "我重构了数据流程。原来的问题是训练数据和评估数据来自同一份原始文件且存在重复，  
> 造成测试集污染。现在我用三层防护：全局去重消除重复样本、  
> 用固定随机种子做 8:1:1 分层划分并物化落盘、  
> 让训练脚本在代码层面无法访问测试集。  
> 并且我写了一个自动化的泄漏自检函数，它能输出三份数据之间的文本交集大小，  
> 结果均为 0。"

**这段话的价值远大于一个虚高的准确率数字。**

## 硬伤 2：没有独立测试集 —— 你的"验证集"承担了三个角色

### 原来是什么

`train.py` 第 39-41 行：

```python
train_texts, val_texts, train_labels, val_labels = train_test_split(
    texts, labels, test_size=0.2, random_state=RANDOM_SEED, stratify=labels
)
```

只有两份数据：训练集和"验证集"。然后你用这个"验证集"的准确率去汇报成绩。

### 为什么是问题

在机器学习里，数据集的角色是严格分工的：

| 数据集 | 职责                | 能用几次      |
| --- | ----------------- | --------- |
| 训练集 | 更新模型参数（反向传播）      | 反复用       |
| 验证集 | 调超参、早停、选最优模型、拟合校准 | 反复用       |
| 测试集 | **汇报最终性能**        | **只能用一次** |

为什么测试集只能用一次？因为**只要你根据测试集的结果去改任何东西  
（哪怕只是"要不要把学习率从 2e-5 调到 3e-5"），测试集的信息就泄漏进模型了**。  
用第三次之后，你汇报的就不是泛化能力，而是"你对这个测试集的过拟合程度"。

旧代码把验证集和测试集合并成一个，用它汇报的成绩**天然偏高**。

### 改成什么

切成三路，并且**严格定义测试集的使用纪律**：

- `test.csv` 只在 `evaluate.py` 里被读取；
- `evaluate.py` 在整个项目里只该跑一次；
- 所有调参都在 `val.csv` 上做。

代码里我特意加了一句注释和日志提示，就是在提醒这一点。

### 收益

- 汇报的数字有学术规范背书，经得起追问
- 训练时能更放心地在验证集上调参（不再怕污染测试集）

### 答辩怎么讲

> "我把数据集严格分成 train / val / test 三路，比例 8:1:1。  
> 验证集用于早停和超参选择，测试集**只用于最终性能汇报，且只运行一次**。  
> 这样做的意义是：报告的指标是无偏的泛化能力估计，  
> 而不是对某个特定数据集的过拟合结果。"

# 第二部分：技术能力的升级

## 升级 3：训练配方从"能跑"升级到"标准"

### 原来是什么

`train.py` 的手写训练循环，关键行：

```python
optimizer = AdamW(model.parameters(), lr=LEARNING_RATE)   # 恒定 2e-5
...
for epoch in range(EPOCHS):        # 固定 3 轮
    for batch in progress_bar:
        outputs = model(...)
        loss.backward()
        optimizer.step()
```

### 为什么是问题

四个具体缺陷：

1. **学习率恒定不变。** BERT 微调的标准做法是"预热 + 衰减"。  
   一上来就给 2e-5 的完整学习率，前几步的梯度会把预训练好的权重冲乱——  
   这是微调掉点的常见原因。
2. **固定跑 3 轮，没有早停。** 可能第 2 轮就已经在验证集上到顶了，  
   第 3 轮纯粹在过拟合，但代码照样跑完，然后保存**最后一轮**的权重  
   （而不是最好的那一轮）。
3. **没有混合精度。** 全程 float32，GPU 算力只用了一半。
4. **选模型的指标是准确率。** 类别不均衡时准确率会骗人（详见下文）。
5. **全量固定 padding。** 第 50-58 行一次性把所有样本 pad 到 `max_length=128`：

```python
encodings = tokenizer(texts, truncation=True, padding=True, max_length=MAX_LEN, ...)
```

我统计过，`large_data.csv` 的评论长度中位数是 75 字，大多数远短于 128。  
把它们统统 pad 到 128，意味着**大量计算浪费在填充的无效 token 上**。

### 改成什么

全部换成 HuggingFace `Trainer` + 标准配方：

| 技术             | 实现                                                                  |
| -------------- | ------------------------------------------------------------------- |
| 学习率预热 + 线性衰减   | `warmup_ratio=0.1` + `lr_scheduler_type="linear"`                   |
| 早停 + 回滚最优权重    | `EarlyStoppingCallback(patience=2)` + `load_best_model_at_end=True` |
| 混合精度           | `fp16=True`（有 GPU 时自动启用）                                            |
| 梯度裁剪           | `max_grad_norm=1.0`                                                 |
| 选模型标准          | `metric_for_best_model="macro_f1"`                                  |
| **动态 padding** | `DataCollatorWithPadding`，每个 batch 只 pad 到批内最长                      |

关于**动态 padding**，值得单独说：我在 `SentimentDataset` 里**故意不写** `padding=True`，  
把 padding 交给 collator 在组 batch 时做。这样一句 8 字的评论和一句 8 字的评论放一起，  
这个 batch 就只有 8 个 token 宽，而不是 128 个。

### 收益

- 训练更稳定，不容易掉点
- 自动停在最优轮次，不会因为多跑几轮而变差
- 训练速度提升（FP16 约 2×，动态 padding 再省一部分）

### 答辩怎么讲

> "训练部分我做了标准化改造。原先是恒定的学习率、固定轮数、单精度训练。  
> 现在改用 BERT 微调的标准配方：学习率线性预热 10% 后线性衰减，  
> 配合梯度裁剪保证训练稳定；开启 FP16 混合精度；  
> 引入早停机制，以验证集 Macro-F1 为监控指标，连续两轮不提升就停止并回滚到最优权重。  
> 另外我把全量固定 padding 改成了动态 padding——因为原始数据的评论长度中位数只有 75 字，  
> 却全部被填充到 128，造了大量无效计算。"

## 升级 4：主指标从准确率改为 Macro-F1

### 为什么改

假设测试集里 90% 是好评，10% 是差评。现在有一个**完全废掉**的模型：  
它对任何输入都输出"好评"。

它的准确率是多少？**90%。**

但它的业务价值是 0——差评一条都没识别出来。  
而电商平台要的恰恰是"揪出差评"。

`accuracy` 在类别不均衡时会被多数类主导，是个会骗人的指标。

**Macro-F1** 的做法是：分别算"差评"的 F1 和"好评"的 F1，然后取**算术平均**。  
两个类别权重相同，谁差就拉低总分。这样才是公平的评价。

### 答辩怎么讲

> "我选择 Macro-F1 作为主指标而非准确率。原因是电商评论存在类别分布问题——  
> 如果好评占 90%，一个全部预测为好评的模型也能拿到 90% 的准确率，  
> 但它完全没有业务价值，因为差评全被漏掉了。  
> Macro-F1 对两个类别等权计算，能真实反映模型对少数类（差评）的识别能力。  
> 同时我也报告了 ROC-AUC，它是阈值无关的指标，用来衡量模型纯粹的区分能力。"

## 升级 5：温度缩放 —— 让置信度变得可信

### 原来是什么

`web_app.py` 第 78-89 行：

```python
probs = torch.softmax(outputs.logits, dim=1).cpu().numpy()[0]
confidence = max(pos_prob, neg_prob) * 100

if confidence >= 85 and prob_diff >= 0.5:
    return f"{emoji} {sentiment}", confidence
else:
    return "🤔 无法确定", confidence
```

直接把 softmax 的输出当置信度用，并配了两个阈值条件。

### 为什么是问题

**神经网络有系统性的"过度自信"倾向。** 这不是你代码的错，是模型的通病：  
它说"我有 99% 把握"的时候，真实正确率往往只有 80% 左右。

我实测过你的旧模型，它给出的结果很说明问题：

| 输入          | 旧模型判断  | 置信度       | 问题                 |
| ----------- | ------ | --------- | ------------------ |
| 这个产品质量很好    | 好评     | 99.6%     | 正常                 |
| 物流太慢，差评     | 差评     | 97.5%     | 正常                 |
| **我吃饭了**    | **好评** | **93.2%** | 域外文本，却给了 93% 的高置信度 |
| **帮我查一下订单** | **差评** | **71.8%** | 域外文本，被硬判成差评        |

"我吃饭了"和电商评论毫无关系，模型却给了 93.2% 的置信度。  
**这就是过度自信的典型表现**——模型不会说"我不知道"，它对任何输入都硬给一个答案。

而这也正是旧代码必须写那 59 行 `NON_COMMENT_KEYWORDS` 关键词表的根本原因：  
因为模型的置信度不可信，只能靠人工规则打补丁。

### 改成什么

两步改造：

**第一步：温度缩放（校准）。**  
在 softmax 之前把 logits 除以一个标量 T：

$\text{softmax}(z / T)$

T 在**验证集**上通过最小化 NLL 拟合得到（论文：Guo et al. 2017, ICML）。  
`T > 1` 让分布变平坦、置信度下降，从而贴合真实准确率。

**关键性质：T 只改置信度，不改预测结果。** 因为除以正数不改变大小关系，  
`argmax` 完全不变，所以准确率、F1 一个都不会掉。  
项目在 `calibration.json` 里用 `accuracy_unchanged: true` 把这一点记录了下来。

**第二步：用置信度阈值替代关键词表**（下面单独讲）。

### 收益

`reliability_curve.png` 这张图会直接展示：校准后的曲线明显更贴近对角线，  
ECE（期望校准误差）下降。

### 答辩怎么讲

> "神经网络的 softmax 输出是有系统性过度自信的。我实测发现，  
> 模型对'我吃饭了'这种完全无关的输入也给出了 93% 的置信度。  
> 所以我引入了温度缩放做后处理校准——在验证集上拟合一个温度标量 T，  
> 让模型声明的置信度与真实准确率对齐。  
> 这一点在可靠性曲线上可以验证：校准后曲线明显更贴近理想对角线，ECE 从 X 降到 Y。  
> 需要强调的是，温度缩放是纯后处理，它不改变任何预测结果，只改变置信度，  
> 所以模型准确率完全不受影响。"

## 升级 6：删掉 59 行硬编码关键词表

### 原来是什么

`web_app.py` 第 17-68 行，用关键词列表 + 正则判断输入"是不是电商评论"：

```python
NON_COMMENT_KEYWORDS = ['吃饭', '睡觉', '打游戏', ... '你好', '你是谁', ...]
NON_COMMENT_PATTERNS = [r'^我[吃饭睡觉去]', r'^你[是叫什么]', ...]
...
if not is_likely_comment(text):
    result = "❌ 这不是电商评论"
```

### 为什么是问题

**三个层面都站不住：**

1. **立意矛盾。** 这是一个 AI 项目。一个 AI 项目靠 if-else 关键词表判断内容，  
   本身就否定了"用 AI 理解语义"的立项初衷。评委一定会抓这一点。
2. **永远列不全。** "我去打球了""帮我查下快递""今天心情不好""这个多少钱"  
   ——你的表里都没有，全部会漏过去被当评论分析。
3. **维护成本转移给未来。** 每发现一个漏网之鱼就加一个词，  
   这是个没有终点的维护负担。

### 改成什么

**完全删除关键词表，交给模型自己的置信度。**

逻辑变成：模型对域外文本（非评论）天然会表现出**低置信度**——  
这是它不确定性的自然反映，不需要人工规则去"告诉"它。  
所以我们只需设一个置信度阈值，低于阈值就显示"无法确定"：

```python
"is_uncertain": confidence < threshold
```

### 收益

- 代码减少 59 行，逻辑更简单
- 换模型、换数据都不用改规则表
- 从"规则驱动"变成"数据驱动"，立意上站得住了

### 答辩怎么讲

> "原方案用关键词表判断输入是否为评论，我认为这有两个问题：  
> 一是与'用模型理解语义'的项目立意矛盾；  
> 二是关键词表永远无法穷举，泛化能力差。  
> 我改为完全依赖模型的置信度——模型对域外文本会自然表现出低置信度，  
> 这是它不确定性的正常反映。设置置信度阈值即可实现拒识，  
> 整个逻辑从规则驱动转为模型驱动。"

## 升级 7：批量推理提速 12～20 倍

### 原来是什么

`web_app.py` 第 92-101 行：

```python
def predict_batch(texts):
    results = []
    for text in texts:                    # ← 逐条循环
        result, conf = predict_single(text)   # ← 每次都做完整前向传播
        results.append((text, result, conf))
```

即使传进来 5000 条评论，它也是老老实实跑 5000 次前向传播。

### 为什么是问题

这是**对 GPU 工作方式的误解**。GPU 的强大之处在于大规模并行计算，  
而"每次只算 1 条"等于把跑车当自行车骑。

我实测了你的旧推理方式：

```
200 条评论：
  逐条前向传播      1.38 秒
  批量推理(128)     0.11 秒
  → 提速 12.6 倍
```

数据量越大，差距越明显（因为批量推理还能摊薄模型加载、数据传输的固定开销）。

### 改成什么

`inference.py` 里的 `predict_probs()` 是唯一底层函数，真正的分批：

```python
for start in range(0, len(texts), self.batch_size):     # 0, 128, 256, ...
    chunk = texts[start:start + self.batch_size]
    enc = self.tokenizer(chunk, padding=True, return_tensors="pt")
    logits = self.model(**enc).logits                   # 一次算 128 条
```

### 为什么能快这么多（这个原理一定要理解）

矩阵乘法的耗时**对矩阵"宽度"相对不敏感**。

处理 1 条样本，GPU 要花约 22ms（大部分是固定开销：启动 kernel、搬运数据）。  
处理 128 条一起，只要约 68ms。

**干的活多了 128 倍，时间只多了 3 倍。**

这就是 GPU 的设计意图——用大规模并行来掩盖单次运算的延迟。  
逐条推理让 GPU 99% 的时间在空转，完全浪费了硬件。

### 答辩怎么讲

> "原方案的批量分析接口内部是 for 循环逐条调用单条预测，  
> 每条都做一次完整的前向传播，GPU 利用率极低。  
> 我分析后发现，GPU 上单次前向传播的耗时主要是固定开销，  
> 处理 1 条和处理 128 条的时间只差 3 倍左右。  
> 所以我改成了真正的分批推理，按 128 条一批打包计算。  
> 实测 200 条评论从 1.38 秒降到 0.11 秒，提速 12.6 倍；  
> 数据量越大优势越明显，因为固定开销被进一步摊薄。"

# 第三部分：工程与答辩的加分项

## 加分 8：错误案例自动归因

### 原来是什么

旧 `visualize.py` 第 98-118 行把错误案例**列出来**并保存成 `wrong_cases.csv`，  
但**没有做任何分类**。你只知道"错了 200 条"，不知道"为什么错"。

### 为什么是问题

"列出错误"是数据，**"归纳错误的模式"才是洞察**。

答辩时如果老师问"你的模型在什么情况下会出错？"，  
你可以翻开 3 万多行的 CSV 说"我也没细看"——这很减分。

### 改成什么

`evaluate.py` 的 `attribute_error()` 会把每个错误自动归类到六种模式：

| 错误类型  | 判断依据       | 说明                 |
| ----- | ---------- | ------------------ |
| 长文本截断 | 原文 > 128 字 | 超出 max_len，后半段信息丢失 |
| 过短样本  | 原文 ≤ 8 字   | 上下文不足以判断情感         |


| 转折结构    | 含"但是/不过/可惜"等  | 情感在后半句反转，模型只看前半段   |  
| 否定/贬义词  | 含"不/没/无/差/烂"等 | 中文否定作用域建模弱         |  
| 抱怨式好评   | 真值好评、预测差评     | 如"就是有点贵"，字面像抱怨实为好评 |  
| 反讽/欲扬先抑 | 真值差评、预测好评     | 语义与字面相反            |  
| 标注疑似有误  | 兜底            | 无显著模式，可能原始标注本身错了   |

### 答辩怎么讲

> "我对错误案例做了自动归因分析，把它归纳为六类模式：  
> 长文本截断、过短样本、转折结构、否定作用域、抱怨式好评、反讽。  
> 结果显示占比最高的是 X 类，说明 Y。  
> 针对这个发现，下一步的改进方向是 Z。"

**注意这段回答的结构：发现问题 → 归纳模式 → 指出方向。**  
这是研究者的思维方式，比"我的准确率有 97%"有说服力得多。

## 加分 9：置信度分桶与阈值建议

### 为什么要有

这是把模型从"一个准确率数字"变成"一个可运营的产品"的关键。

`per_bucket_accuracy.png` 会把测试样本按模型把握程度分成 5 档，  
统计每档的准确率和样本占比，然后回答一个非常实际的问题：

> **"如果我要求模型必须有 90% 以上把握才给结论，能覆盖多少数据？准确率是多少？"**

有了这个表，阈值就不再是拍脑袋定的（旧代码是硬写 85% 和 0.5 两个魔数），  
而是有数据支撑的决策。

答辩时你可以说：

> "我们的系统采用分级策略：对置信度 ≥ 90% 的样本（占 X%，准确率 Y%）  
> 直接给出结论；对置信度在 70%～90% 的样本标记为'建议人工复核'；  
> 低于 70% 的直接拒识。这样在保证 Y% 准确率的前提下，  
> 能自动处理 X% 的数据量。"

**这就是"工程思维"，是评委最容易给高分的部分。**

## 加分 10：可复现性

### 原来是什么

`train.py` 第 18 行定义了 `RANDOM_SEED = 42`，也传给了 `train_test_split`，

但**没有固定 PyTorch 和 NumPy 的随机源**。

### 为什么是问题

BERT 微调里的随机性来源很多：权重初始化、Dropout、数据打乱顺序。  
不固定这些，同一个脚本跑两次结果能差 1～2 个点。

后果是：**你没法判断"我这次的改动到底有没有用"**——  
因为改进 1 个点的改动，可能被随机波动的 2 个点淹没。

### 改成什么

`utils.py` 的 `set_seed()` 固定三层随机源：

```python
random.seed(seed)
np.random.seed(seed)
torch.manual_seed(seed)
torch.cuda.manual_seed_all(seed)
torch.backends.cudnn.deterministic = True    # 让 cuDNN 用确定性算法
torch.backends.cudnn.benchmark = False
```

### 答辩怎么讲

> "为了保证实验可复现，我固定了 Python、NumPy、PyTorch、CUDA 四层的随机种子，  
> 并启用了 cuDNN 的确定性模式。这样同一个脚本任意跑多少次，  
> 结果都是一致的——这是做对比实验的前提，  
> 否则无法判断某个改动的效果是真实的还是随机波动的。"

# 最后：关于拿这个项目去比赛

## 能参加什么比赛

**适合：**

- 中国大学生计算机设计大赛（软件应用与开发类）
- 服务外包创新创业大赛
- 挑战杯 / 互联网+ 的软件应用赛道
- 各类"人工智能应用"类校级、省级竞赛

**不适合：**

- 各类算法竞赛（ACM/ICPC）、CSP、Kaggle 这类
- 原因：那些是**算法创新**导向，比的是模型结构和指标的极限。  
  本项目是**工程应用**导向，用的是现成预训练模型。  
  强行投算法类比赛，会被"创新性不足"这条打回来。

## 答辩时的胜负手

**记住这句话：评委不关心你用了 BERT，因为人人都会用 BERT。**

你的项目里真正稀缺的能力是这三样：

1. **对数据泄漏的敏感度**（硬伤 1）  
   —— 说明你知道科研的底线在哪
2. **对模型不确定性的处理**（升级 5、6、9）  
   —— 说明你知道模型不是万能的，会设计降级策略
3. **对性能瓶颈的定位能力**（升级 7）  
   —— 说明你懂硬件、能优化

这三样都&#x662F;**"知道模型会怎么坏，并提前防住"**&#x7684;能力。  
比"我的准确率 97%"要值钱得多——因为那个 97% 别人也会刷。

## 还想再提升，下一步做什么

按性价比排序：

1. **换更强的预训练模型**（改 `config.py` 一行）  
   `bert-base-chinese` → `hfl/chinese-roberta-wwm-ext`，通常 +1~2 个点
2. **扩充训练数据**  
   数据量和多样性往往比模型结构更影响效果
3. **做成三分类**（好评/中评/差评）  
   更贴合真实业务，也更有技术讨论空间
4. **加细粒度情感**  
   从"好/差"细化到"物流/质量/客服/价格"多维度
5. **领域自适应**  
   用你的目标领域无标注数据做继续预训练（DAPT）
